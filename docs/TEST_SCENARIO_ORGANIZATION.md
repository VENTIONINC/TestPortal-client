# Test Scenario organization

The Scenarios catalog shows all scenarios, a folder and optionally its descendants, or scenarios with no folder. The folder tree shows direct counts aggregated through descendants; All scenarios and No folder counts are independent of the current search and filters. The final No folder entry follows the nested folder tree. Suites keep their existing membership view.

The Scenarios list uses project-scoped server pagination with 10, 25, 50 or 100 rows per page (25 initially). Search matches title and scenario key. Priority and Author filters combine with search and folder scope. Priority supports selecting multiple values; Done applies the selection and Clear removes it. Counts beside each priority reflect the current scope and other filters, independent of the selected priorities. Sorting is explicit by Key, Title, Folder, Updated or Author, with Updated descending initially. Each row shows summary fields only; details and Markdown remain on the scenario page. Full title, folder path and author identity remain accessible when the compact row truncates them.

Folders belong to one project and can be nested. Create from a selected folder to create a child folder. Folder descriptions are optional; leaving the description unchanged on an update preserves it, while clearing the field saves no description. The selected folder description appears below its name. Moving a folder changes its parent; folder deletion asks whether direct scenarios should move to the parent or to No folder. Child folders are promoted to the deleted folder's parent.

Suites are current, ordered selections of existing scenarios. Their purpose, description and release are labels only; a release suite does not preserve historical run evidence. Members can be added or removed in sequential batches of at most 100 scenarios, and the catalog can reorder suite members. Scenario forms can assign a folder or leave the scenario without a folder. Moving scenarios, editing folders, or changing suite membership does not change scenario identity or execution history.

Selecting rows affects their UUIDs and can persist across pages, page-size changes and sorting while matching criteria stay the same. The page checkbox affects only visible rows; Shift-select affects the visible ordered range. **Select all N** resolves the complete matching UUID set from the server and labels the toolbar as all matching scenarios. Changing project, folder scope, descendant mode, search, Priority or Author clears selection. A failed or stale all-results resolution does not install IDs.

Bulk **Move…** assigns scenarios to a folder or No folder in All scenarios, folder and No folder views. Drag a row handle onto a folder or No folder to move it; dragging a selected row moves the full selection, including UUIDs from other pages, and dragging an unselected row moves just that row. Dragging never changes scenario or suite order. Folder moves are hidden in Suites. **Add to suite** and confirmed **Delete** use the selected UUID snapshot. Operations run sequentially in batches of at most 100 and stop on the first failed batch. Confirmed successes are removed from selection; failed, uncertain and unattempted IDs remain selected. No mutation is retried automatically.

Recovery example: if 237 IDs are selected and the second Move request returns a conflict, the first 100 are reported as succeeded, the next 100 as failed, and the final 37 as not attempted. The first 100 are removed from selection, and the unresolved 137 remain selected. Review the reported error and current folder state, then explicitly retry or choose another action. A transport or server error is reported as uncertain and also requires checking current state before retrying.

Delete first presents the exact selected count. Cancel makes no delete calls. Confirmation deletes the captured UUIDs one by one, stops at the first failure, refreshes server-backed lists and counts after confirmed results, and adjusts the page if deletion leaves it past the last available page.

Create and edit use one draft workspace. Keys are assigned by the server on Save (`TMS-N`) and cannot be edited. Priority starts at Medium. **Save scenario** or **Save changes** submits fields, folder, ordered steps and all suite selections together. Blank new step rows are ignored; a row containing only an expected result and a saved row with a cleared action must be corrected.

Use **Add step** to append and focus its action, or Enter in the last row's expected result. Shift+Enter inserts a line break. Drag a row by its handle; with the keyboard, press Space to pick up, Arrow Up/Down to reorder and Space to drop. Changes remain local until Save.

The Suites picker searches existing project suites and shows their scenario counts. Creating a suite in this picker adds a local selected tag: the suite is created only by the final scenario Save. Removing the tag or cancelling creates nothing. Back and Cancel return to the current draft folder (or Unfiled), after confirming any unsaved changes. Navigation, project changes and browser exit also guard dirty drafts.

If a save reports a stale scenario or membership conflict, the whole draft stays available. **Reload saved scenario** asks before discarding it; a failed reload preserves the draft. Suite-name collisions can be corrected by removing the new tag and selecting the existing suite. A transport failure during creation can leave the result uncertain: inspect the catalog before explicitly retrying. History shows the creator and most recent updater; unavailable attribution is shown as Unknown.
